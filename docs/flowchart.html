Bus side layout: who does what

From one entry-side photo and user-supplied dimensions to a rendered boxy bus. The VLM judges, OpenCV measures, plain code does the arithmetic. Two VLM calls per bus, both returning small JSON.

Actors

User

Supplies brand, model, length, wheelbase, front overhang, base colour and one entry-side photo.

Their values override everything else.

Code

Validation, arithmetic, the 1D homography, sanity checks and JSON assembly. Python or Java.

Deterministic, no inference.

VLM subagent

Judgment: where things roughly are, and what each proposed box is.

Never counts, never measures pixels.

OpenCV

Precise pixels: scans the window band, finds pillar edges, draws the numbered overlay.

Over-segments on purpose; the VLM decides.

three.js SPA

Reads vehicle.json and renders the fixed boxy bus with a template front and brand badge.

No photo, no inference.

Flow

Sobel: finding pillars by edges

A Sobel filter measures how sharply brightness changes from one pixel to the next, here left to right. Flat areas, like the inside of a window or a painted panel, score near zero. The border between glass and a pillar scores high.

OpenCV averages the score down each column of the window band, giving one number per column. Every pillar then shows up as a pair of peaks, one for each of its edges.

This still works where colour fails: black pillars behind flush glazing usually keep a visible frame edge. The catch is that reflections, stickers and seals make peaks too. So OpenCV keeps every peak as a possible boundary, and the VLM throws out the false ones in pass 2.

Four anchors: pixels to millimetres

In a photo, equal lengths along the bus don't take equal pixels. The far end is squeezed, so one mm-per-pixel scale would place every window wrong.

Along a straight line seen in perspective, pixel column u maps to position x by a 1D projective map, x = (a·u + b) / (c·u + 1). It has three unknowns, so three points known in both pixels and mm fix it.

The user's dimensions give four such points for free: front end at 0, front axle at the front overhang, rear axle one wheelbase further, rear end at the full length. The VLM only has to say where they are in the photo.

The fourth point is the check. Fit the map on all four and look at the leftover error: if one anchor misses by more than about 1–2 % of the length, pass 1 put it in the wrong place, typically a cut-off bus end or a wheel centre misread, and the sanity check fails.

This assumes vertical edges look vertical, which holds for a roughly level camera, so a pillar's pixel column is the same at wheel height and window height.

How the 1D map drives the sanity checks

Each anchor gives one equation, and the map has three unknowns. Rewritten as a·u + b − c·u·x = x it is linear, so fitting is plain least squares. Four anchors means one spare.

Use the spare one at a time: fit on three anchors, predict where the fourth should land in mm, and compare with its known position. Doing this for each of the four shows which anchor is wrong, not just that one is. The steered front wheel and a cropped bus end are the usual suspects.

The map also makes the feature checks possible. In pixels, the far windows look narrower than the near ones, so “all windows are about the same width” can only be tested after converting to mm.

The map checks need only pass 1 and the dimensions, so they can run before OpenCV starts. Thresholds are starting points to tune on real runs.

Why OpenCV draws numbered boxes for the VLM

Asked “how many windows are on this bus?”, a VLM often gets the number wrong: models are unreliable at counting rows of similar-looking things.

So the VLM is never asked to count. In the Numbered overlay step, OpenCV draws a box with a number around every segment it found between possible pillars, and sends that marked-up photo to the VLM. In Pass 2: label boxes, the VLM answers one small question per box: is box 3 a window, a door, a pillar, or half a window that belongs with box 4?

Code then merges the halves and counts the boxes labelled window. The count comes from a list, not from the model’s guess.
